# Phase 2 — first delivery: catalog and dispensing baskets

Phase 2 is **in progress**, not complete. This delivery starts PHARM-01–04 and FIN-01. The [implementation tracker](IMPLEMENTATION_TRACKER.md) retains purchasing, replenishment, reporting, combined payment retry protection and linked returns/reconciliation as unfinished work. Workforce and management requirements requested on 30 September are also recorded there for the next management workstream.

## Delivered

- Searchable medicine catalog linked one-to-one to existing inventory items. Stock codes, historical prescriptions, quantities and dispense records are not renamed or rewritten. Metadata includes generic name, ingredients, strength, dosage form, route and brand; review and active flags prevent unreviewed basket supply.
- Barcode aliases, including package barcodes linked to existing package-unit definitions. Leading zeroes are preserved. Cross-item package mappings and ambiguous code/barcode collisions are rejected. A system administrator can deactivate incorrect aliases without deleting their history.
- Patient-bound, facility-scoped dispensing baskets with open/held/completed/cancelled states, revision checks, audited changes and soft removal of lines. Holding does not reserve stock. Repeated scans create explicit separate lines for staff review rather than silently adjusting another item.
- Snapshot of medicine identity, package conversion, prescription directions and reviewed unit price at line entry. Checkout rejects changed identity/price/package/directions and requires removal/re-addition for review. Base-unit quantity is validated; duplicate Rx lines are aggregated against the outstanding prescription.
- Atomic checkout through the existing dispense service. It locks stock, excludes expired/quarantined/other-facility batches, allocates earliest-expiry batches first, updates Rx progress and records stock movements and a dedicated invoice. A failed action rolls back all effects. Repeated completion returns the original invoice using a per-basket checkout key.
- Medicine instruction labels using recorded medicine and Rx snapshots plus actual allocated batch records. No dosage or safety instructions are generated by the system; staff review the supplied instructions and packs.
- Invoice handoff to the existing cashier queue/workspace. No payment is collected implicitly, and pharmacists do not gain cashier access. Positive invoices become ready-to-pay; zero-total invoices have no balance due. Line amounts are rounded by the existing invoice system per batch allocation, so a fractional split can differ from the pre-allocation estimate by a rounding amount.

## Access and pharmacy policy

Pharmacy/admin staff can create and operate baskets only for permitted patients; cashiers cannot perform this dispensing action. Catalog reads are available to pharmacy, clinical, store and managerial roles. Because inventory codes and catalog metadata are currently shared across facilities, catalog writes require a system superuser. Facility admin/manager users can maintain their assigned facility's retail switch.

Retail supply defaults to **disabled**. No-prescription supply requires both a reviewed, active catalog profile marked non-prescription and the facility retail switch. The same checks run inside the existing UI/API dispense service to avoid a bypass. Existing prescription-based legacy supply without a catalog profile retains its prior behavior; once a profile exists, its review/active checks apply. New baskets always require a reviewed profile. This is a configurable operational rule, not a claim that medicine classifications comply with every facility policy or regulation.

## Upgrade and initial setup

1. Back up the database and private media. Run `python manage.py migrate` and `python manage.py collectstatic --noinput` after pulling the release.
2. Pharmacy migration 0004 creates catalog/basket/history records. Migration 0005 maps existing stock items to **unreviewed** profiles; it does not guess clinical classifications. Operations migration 0016 refreshes canonical-patient guards to include basket, line and allocation paths.
3. Before reopening dispensing, review imported medicine profiles at `/pharmacy/catalog/`, configure prices through existing price-list setup, verify base stock units/package factors and add barcode aliases. Imported profiles require review even on legacy dispensing paths.
4. Enable facility retail supply at `/pharmacy/policy/` only after approving classifications and the local workflow. Keep it disabled if all supply should require a prescription.
5. Start from Pharmacy → Dispensing baskets, or from the patient's Rx → Start a basket. Add a code/barcode, package quantity and matching Rx line, review the basket, dispense, print labels and hand the patient to cashier.

Use PostgreSQL for concurrent dispensing. SQLite regression tests do not prove row-lock behavior. Rollback of schema changes after actual dispensing requires the normal backed-up deployment recovery procedure; do not delete live financial/stock records to reverse a release.

## Verification and remaining acceptance

New tests cover FEFO splits, stock-shortage rollback, failure after a first allocation, retry-safe completion, held/cancelled/stale baskets, package conversions, price/Rx changes, barcode ambiguity, retail policy, cross-facility/role access and patient-merge guards. PostgreSQL tests contend two different patients for the final unit and replay the same basket concurrently. Browser checks cover 390/768/1440 widths and the add/hold/resume/dispense/print-label journey.

Facility staff still need to validate actual catalog classifications, package factors, hardware scanners and label printers. A pharmacy basket is a dispensing/invoice workflow in this release; it is not yet the complete R2 linked payment/return/reconciliation suite. Existing cashier collection and reviewed refunds remain separate.

Technical references reviewed: [Django 5.2 transaction management](https://docs.djangoproject.com/en/5.2/topics/db/transactions/) and [QuerySet row-lock behavior](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#select-for-update). Contention tests use real transactions on PostgreSQL, rather than interpreting SQLite test success as concurrency evidence.
